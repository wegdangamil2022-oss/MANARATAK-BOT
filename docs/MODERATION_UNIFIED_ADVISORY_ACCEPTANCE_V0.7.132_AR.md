# بوت منارتك v0.7.132 — محضر قبول فني موحد لتجربة إشراف Telegram

## الهدف والحدود

أضيف محضر **استشاري فقط** يجمع الأدلة التقنية عن مجموعة تجربة واحدة وعضو متطوع، مع إعلان ما لا تستطيع البرمجيات إثباته. المحضر لا يعتمد تجربة بشرية، ولا يفعّل العقوبات الحية، ولا يكتب إيصال موافقة في قاعدة البيانات، ولا يعد بتثبيت صلاحيات Telegram بعد الفحص.

تُنشئ الدالة `inspectModerationTrialAcceptanceReadOnly` تقريرًا من جلسة `GROUP → TARGET → GROUP` المتصلة؛ وهي تستعمل فحوص المجموعة والعضو وحقوق البوت ومطابقة نسخة SQLite الاحتياطية وملف `STOP` الخاصة بالإصدارات السابقة. يحفظ التقرير نتائج عامة **دون** عناوين المجموعات ومعرّفاتها أو حسابات الطلاب أو مسارات الملفات أو رمز Telegram.

## محتويات المحضر

- `stage: READ_ONLY_MODERATION_ACCEPTANCE`: نوع التقرير.
- `status: TECHNICAL_PASS | BLOCKED`: صلاحية الأدلة التقنية المقروءة لحظة الفحص فقط.
- `safety`: قيمة `STOP` أو `RUN` أو `UNKNOWN` إن كانت البيانات غير سليمة.
- `rollback`: حالة مطابقة نسخة SQLite الاحتياطية.
- `botRights`: صلاحية بوت Telegram للإشراف.
- `group`: نوع المحادثة بعد التحقق من هوية المجموعة مرتين قبل العضو ومرتين بعده.
- `target`: أهلية العضو البشري المحدد للتجربة فقط.
- `reasons`: أكواد منع عامة ثابتة، لا رسائل خام من Telegram.
- `operatorChecks`: فحوص بشرية معلقة لا يمكن اعتمادها آليًا.
- `operatorApproved: false` و`authorizedToSendSanctions: false` و`liveModeration: DISARMED`: لا تتغير بسبب نجاح الفحص التقني.

### الشروط البشرية التي لا تزال معلقة حتى بعد TECHNICAL_PASS

1. تأكيد المالك أن المجموعة تجريبية معزولة وغير مستخدمة من طلاب حقيقيين.
2. إثبات موافقة العضو المتطوع على اختبار قد يؤثر في حسابه.
3. مراجعة خطة التراجع واستعادة نسخة البيانات والطريقة الصحيحة للتعامل مع حظر أو كتم وصل فعليًا إلى Telegram.
4. الحصول على موافقة صريحة من مالك المشروع قبل أي تجربة تنفيذية مستقلة.

**نجاح هذه الشروط البشرية خارج نطاق هذا المحضر**. لا توجد داخل البوت آلية تعتمدها تلقائيًا أو تفعّل `BAN` أو `MUTE` بناء على هذا التقرير.

## تشغيل المحضر

بعد إعداد مجموعة اختبار فعلية معزولة، وتحضير SQLite محليًا ونسخة احتياطية مستقلة وملف `STOP\n` خاص بصلاحيات مقيدة، استخدم متغيرات البيئة `TELEGRAM_BOT_TOKEN` و`BOT_OWNER_ID` عبر مدير أسرار، ثم:

```bash
npm run telegram:moderation-acceptance -- \
  --offline-only \
  --state /private/trial/state.sqlite \
  --backup /private/trial/rollback.sqlite \
  --safety /private/trial/telegram.stop \
  --stale-ms 900000 \
  --trial-chat -1001234567890 \
  --trial-target 300123456
```

المسارات والمعرفات هنا **أمثلة غير حقيقية**. لا ترسل الرمز أو ملفات SQLite إلى الدردشة أو GitHub.

رمز الخروج `0` يعني نجاح الفحص **التقني الاستشاري فقط**؛ `2` يعني المنع؛ `1` يعني خطأ تشغيل/إعداد. لا تستخدم رموز الخروج كسماح لتنفيذ عقوبة أو رفع `STOP`.

## سلوك منع الخطأ

- يُعاد فحص المجموعة والعضو والمجموعة والحقوق والنطاق المحلي خلال جلسة واحدة.
- أي نتيجة `PASS` متناقضة مع `RUN` أو نسخة احتياطية غير متطابقة أو مجموعة غير مناسبة أو عضو محمي تُحوّل إلى `BLOCKED` مع `TRIAL_ACCEPTANCE_EVIDENCE_INCONSISTENT`.
- تُمرّر فقط أسباب منع من قائمة رموز ثابتة معروفة؛ لا يدخل نص Telegram الخام أو رسائل أخطاء الملفات في المحضر.
- تبقى الشروط البشرية غير معتمدة حتى لو كان جميع الأدلة التقنية مطابقًا.

الاختبارات تُشغل بوابات HTTP وهمية ولا تُجري اتصالات عقوبات Telegram حية. لم يطرأ أي توصيل جديد لبوابة العقوبات في `createLiveTelegramServer`.
