# المرحلة الثالثة — أوامر الإشراف بالرد والتجربة المحلية

## ما بُرمج

يربط TelegramUpdateApplication أربعة أوامر صريحة بخدمة ModerationService الموجودة، عند حقنها صراحة في إعداد التطبيق:

| الأمر داخل مجموعة معتمدة، بالرد على رسالة عضو | الأثر |
|---|---|
| `/ban case-id` | إضافة سبب حظر يدوي عبر سجل العقوبات وبوابة الإشراف المهيأة |
| `/mute case-id` | إضافة سبب كتم يدوي عبر الخدمة نفسها |
| `/warn case-id` | تسجيل تحذير محلي بعد التفويض وفحص حقوق البوت وحماية الهدف |
| `/unwarn case-id` | إلغاء التحذير ذي المرجع نفسه وفق الصلاحيات الحالية |

`case-id` مرجع قصير من الأحرف الإنجليزية والأرقام والشرطة والشرطة السفلية، وليس نصًا حرًا أو اسم مستخدم. تقبل الصيغة `/ban@ManaratakBot case-id` أيضًا عندما تطابق هوية البوت المهيأة. لا تنفذ الأوامر الموجهة إلى بوت آخر.

يؤخذ العضو من مؤلف الرسالة المردود عليها مباشرة في المجموعة نفسها. تُرفض الرسائل المنقولة أو المجهولة أو المرسلة باسم قناة، والبوتات، ومعرفات الرسائل غير الصالحة، والرد المفقود. لا يُبحث في تاريخ المجموعة ولا تُحوّل أسماء المستخدمين أو النصوص إلى هوية هدف.

صلاحية moderation مستقلة عن navigation: لا يشترط وجود مكتبة تعليمية حتى يدير المشرف مجموعة مخولة. تبقى هوية الفاعل وصلاحية المجموعة وحقوق البوت وحماية المالك والمشرفين وحدود المعدل وتداخل أسباب القيود وخطوات INTENT/STARTED/النتيجة داخل الخدمة المشتركة، دون محرك عقوبات موازٍ.

## النتائج والخصوصية

- لا تُنشر هوية العضو أو مرجع الحالة أو عدّاد التحذيرات في رد عام للمجموعة. في هذه الشريحة يعود قرار المعالجة عبر نتيجة المعالج ويُحفظ في التدقيق؛ لم تُضف رسالة عامة أو واجهة تأكيد للعقوبات بعد.
- تكرار update_id لا يعيد التنفيذ. وجود INTENT أو STARTED أو UNKNOWN_OUTCOME يمنع إرسال عقوبة جديدة على الهدف بحسب قواعد الخدمة.
- أخطاء التخزين/النقل التي تصل إلى هذا المحول تعود UNKNOWN مع سبب عام، ولا تتحول إلى نجاح أو إعادة إرسال.
- APPLIED في المعالج هو نتيجة بوابة الإشراف المحقونة؛ إثبات مصدرها موجود في moderationOperations.attemptGateway. الاختبارات الوهمية لا تثبت نجاح عقوبة في Telegram الحقيقي.
- يستدعي تسجيل التحذير الآن فحص الصلاحيات الخارجية وحماية الهدف قبل المعاملة، ثم يعيد فحص التفويض الداخلي داخل المعاملة. لم تعد حماية Telegram الخاصة بالهدف مقتصرة على BAN/MUTE.

## التجربة المحلية

```bash
npm run demo:moderation
```

ينشئ الأمر SQLite مؤقتة ببيانات وهمية، ويستخدم TelegramBotApiModerationGateway مع بديل طلب HTTP محلي لا يخرج إلى الشبكة. يجرب حظرًا وكتمًا وتحذيرًا وإلغاءه، وتكرار Update، وtimeout مجهولًا ثم محاولة ثانية محجوبة، وإيقاف البوابة قبل أثر جديد. يحذف المجلد المؤقت ويطبع نتائج عامة فقط. لا يقرأ أسرار البيئة أو يجهز مجموعة حقيقية أو يغيّر ملف STOP/RUN.

الاختبارات في `telegram-moderation-commands.test.ts` تختبر المسار عبر تطبيق التحديثات على JSON وSQLite، وتتحقق من حمولة banChatMember وبصمة مصدر TELEGRAM_API باستخدام نقل وهمي، ومن عدم الإرسال عند STOP. اختُبر فشل حماية التحذير أولًا ثم أُصلح.

## ما لم يُغلق بهذه الشريحة

خادم التشغيل الحالي لا يحقن منفذ الأوامر الجديد؛ لا تُفعّل التجربة المحلية العقوبات الحية تلقائيًا. يلزم استكمال واجهات المعاينة والتأكيد والتشغيل وربطها وتجربتها قبل إعلان الجاهزية.

فك الحظر والكتم، والمدد والطرد والحذف والقفل والفلاتر ومكافحة السبام ليست منفذة بهذا المحول. بوابة Telegram الحالية ترفض NONE؛ لا تُنشأ أوامر توهم برفع القيود أو تستبدل الأذونات القديمة بفتح شامل. لا يجوز إعلان المرحلة الثالثة مكتملة اعتمادًا على هذه الشريحة.
