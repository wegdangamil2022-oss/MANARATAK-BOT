# منارتك v0.7.123 — اتساق ملف الإيقاف والنسخة الاحتياطية خلال الجاهزية

## الخلل الذي أثبتته اختبارات الفشل أولًا

فحص الجاهزية المحلي للقراءة فقط `inspectTelegramTrialAcceptanceReadOnly` كان يتحقق مرتين من القيمة `STOP`، لكنه لا يقارن هوية الملف وإصداره عبر القراءتين. إذا استُبدل ملف STOP بملف آخر يحمل المحتوى نفسه قبل إعادة الفحص، أمكن أن يظهر `PASS`.

كذلك فحصت الجاهزية النسخة الاحتياطية SQLite مرة واحدة، ثم اعتمدت في نهاية الفحص على رقم inode وحجم الملف وmtime. تعديل محتوى صف موجود في SQLite مع إرجاع حجم الملف وmtime إلى القيمة السابقة ترك تقرير `PASS` مع أن دليل النسخة الاحتياطية تغير.

## المعالجة

- أصبح فحص الجاهزية يتحقق من ثبات هوية ملف STOP ومعلوماته الأساسية عبر مراحل الفحص: الجهاز وinode والحجم والحقوق وعدد الروابط وmtime/ctime بدقة النانوثانية حيث يدعمها نظام الملفات.
- أصبحت لقطة النسخة الاحتياطية تُقرأ **مرة ثانية** بالآلية المحمية للقراءة فقط. تُقارن اللقطتان منطقيًا، ولا تكفي المساواة السطحية بين حجمي الملفين أو تواريخ التعديل.
- تمت إضافة مقارنة زمن تغيير inode (`ctime`) ومعلومات المحتوى الرئيسية لملفي قاعدة البيانات؛ وهذا يكشف أيضًا بعض حالات التعديل ثم إرجاع mtime أو المحتوى السابق.
- عند اكتشاف تغيّر في الدليل يُرمى الخطأ الثابت `TRIAL_ACCEPTANCE_STATE_CHANGED`؛ يعرض CLI رمزًا عامًا دون معلومات عن المجموعات أو الطلاب أو المسارات أو الرموز السرية.
- لا يتم إصلاح أي قاعدة بيانات، ولا تُنشأ نسخة احتياطية تلقائيًا، ولا يتغير ملف STOP، ولا يُرسل أي طلب Telegram، ولا تُفعّل عقوبات.

## الاختبارات

أُضيفت حالات SQLite جديدة تحاكي الاستبدال الذري للملف STOP بملف خاص آخر يحمل `STOP\n`، وتعديل قيمة موجودة بالنسخة الاحتياطية في مكانها مع استعادة الحجم وmtime، والحالة الطبيعية التي تظل `PASS`. إثبات الفشل قبل الإصلاح في GitHub Actions؛ تحقق نجاح الاختبارات النهائية يظهر في طلب الدمج.

هذه الفحوص استشارية فقط: حتى `PASS` لا يثبت عزل نظام الملفات عن كاتب خارجي غير موثوق، ولا يمنح إذنًا لتغيير `STOP` إلى `RUN`. يجب إيقاف الكتّاب وتقييد أذونات الدليل قبل فحص تشغيل تجريبي.
