# بوت منارتك v0.7.131 — فحص المجموعة والعضو في جلسة متصلة واحدة

## لماذا هذه الدفعة؟

أصبح لدى منارتك فاحص منفصل لهوية المجموعة وفاحص منفصل لأهلية العضو التجريبي. كلاهما يعيد فحص `STOP` وصلاحية البوت ونسخة قاعدة البيانات احتياطيًا؛ لكن اجتياز فحص المجموعة ثم فحص العضو كعمليتين مستقلتين لا يثبت أن هوية المجموعة ما زالت نفسها **بعد انتهاء فحص العضو**.

يضيف هذا الإصدار جلسة `inspectContinuousModerationTrialReadOnly` تقوم بفحص **المجموعة → العضو → المجموعة من جديد**. ليس في النتيجة الإيجابية أي إذن بتنفيذ حظر أو كتم.

## مسار القراءة

1. يُرفض إدخال معرّف عضو غير صالح أو اختيار مالك البوت قبل أي اتصال مع Telegram أو قراءة الملفات.
2. تُؤخذ نقطة تحقق أولى من ملفات SQLite الأساسية والنسخة الاحتياطية وملف `STOP` الخاص.
3. يُنفذ الفحص الرسمي لهوية المجموعة: تحقق اعتماد مجموعة واحدة، الأرشيف خالٍ من سجل عقوبات التجربة، مطابقة النسخة الاحتياطية، صلاحية البوت `can_restrict_members` مرتين، وهوية المحادثة ونوع `group` أو `supergroup` مرتين باستدعاء `getChat`.
4. تُقارن ملفات التشغيل بنقطة التحقق الأولى؛ تغيير رقم الملف `inode` أو المحتوى/البيانات الزمنية يحجب الاستمرار.
5. يُفحص العضو مرتين `getChatMember`، ويُقبل استشاريًا فقط إن كان حسابًا بشريًا عاديًا وليس مشرفًا أو المالك أو بوتًا، مع تكرار فحوص صلاحيات البوت والنطاق والملفات.
6. بعد فحص العضو، يُعاد فحص **هوية المجموعة ونوعها** مرتين مع قراءة حقوق البوت مرة أخرى. تحول `supergroup` إلى نوع آخر، أو سحب حق البوت، أو فقدان النطاق، أو تعطل القراءة، يعني `BLOCKED`.
7. عند النهاية يُعاد التحقق من قبول التجربة المحلي ومن نفس نقطة تحقق الملفات. تتطلب `PASS` نجاح **جميع** المراحل ضمن الجلسة نفسها.

في المسار الطبيعي المستقر تتم ثماني عشرة قراءة `getChat`/`getChatMember` موزعة على مراحل المجموعة والعضو والمجموعة. هذا العدد ليس ضمانًا زمنيًا؛ يمكن أن تتغير صلاحيات Telegram بعد آخر قراءة مباشرة.

## الأمر الموجود الذي أصبح يعتمد الجلسة المتصلة

```bash
npm run telegram:moderation-target -- \
  --offline-only \
  --state /private/trial/state.sqlite \
  --backup /private/trial/rollback.sqlite \
  --safety /private/trial/telegram.stop \
  --stale-ms 900000 \
  --trial-chat -1001234567890 \
  --trial-target 300123456
```

يحتاج الأمر إلى `TELEGRAM_BOT_TOKEN` و`BOT_OWNER_ID` من متغيرات بيئة محمية، وليس معاملات سطر الأوامر. المسارات والمعرّفات أعلاه أمثلة افتراضية فقط.

مخرجاته الآن من النوع `READ_ONLY_MODERATION_TRIAL` وتحتوي على `status` و`group` و`target` و`botRights` وأسباب عامة فقط؛ لا يعرض مفتاح Telegram أو عنوان المجموعة أو معرّفات الأشخاص أو مسارات التخزين.

## تفسير النتيجة

- `PASS`: الأدلة المقروءة اجتازت الفحص الاستشاري في تلك اللحظات، وليس تصريحًا بتفعيل العقوبات.
- `BLOCKED`: لا ترفع ملف `STOP` ولا تحاول التحايل على السبب. إذا تغيرت هوية المجموعة أو ملف الإيقاف، أعد إعداد التجربة من الأساس بعد المراجعة.
- `TRIAL_REMOTE_CHAT_KIND_CHANGED`: تغير نوع المجموعة بين مرحلتي فحص المجموعة، حتى لو بدت عضوية الشخص سليمة بينهما.
- `TRIAL_CHECKPOINT_CHANGED`: تغيرت ملفات المصدر أو النسخة الاحتياطية أو ملف الإيقاف أثناء الجلسة.

## حدود الأمان

- لا تنفذ الوظيفة `banChatMember` ولا `restrictChatMember` ولا تغيّر قاعدة البيانات أو ملف `STOP`.
- تستعمل اختبارات المستودع بوابة اتصال وهمية، وليست دليلًا على تجربة شبكة Telegram الحقيقية.
- لا تثبت فحوص `getChat` و`getChatMember` أن المجموعة معزولة عن أشخاص حقيقيين أو أن المشرفين الآخرين لن يغيروا حالة العضو.
- لا تزال العقوبات الحية غير موصولة داخل خادم التشغيل `createLiveTelegramServer`. يلزم تدخل المالك، وعزل مجموعة خاصة، والتحقق من الحقوق وخطة التراجع قبل أي اختبار مؤثر.
