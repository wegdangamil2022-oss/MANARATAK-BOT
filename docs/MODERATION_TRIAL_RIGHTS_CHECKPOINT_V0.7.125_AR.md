# بوت منارتك v0.7.125 — تثبيت دليل فحص صلاحيات Telegram أثناء التجربة المعزولة

## الخلل المثبت قبل الإصلاح

يفحص `inspectIsolatedModerationRightsReadOnly` صلاحيات البوت في Telegram مرتين، وتحيط بهما فحوص قبول SQLite وحالة `STOP`. كانت هذه الفحوص منفصلة: إذا استُبدل ملف STOP بملف خاص آخر يحمل `STOP\n`، أو استُبدلت النسخة الاحتياطية بنسخة **مطابقة منطقيًا**، بين الفحوص المتعاقبة، أمكن أن تنتهي النتيجة `PASS`. لا يعني هذا أن Telegram تعرض لطلب عقوبة؛ إنما لا يصح اعتبار دليل التجربة ثابتًا خلال الانتظار على الشبكة.

## ما تغير

1. بعد نجاح الفحص المحلي الأول، تؤخذ بصمة زمنية للملفات الثلاثة: قاعدة SQLite الرئيسية، والنسخة الاحتياطية، ومفتاح STOP.
2. تتم مقارنة هذه البصمة قبل الاعتماد على فحص الصلاحيات الثاني، وعند نهاية الفحص بعد القراءتين.
3. تُقارن هوية الجهاز والملف `dev/ino`، والأذونات، وعدد الروابط، والحجم، ووقت تعديل البيانات `mtimeNs` ووقت تغيير وصف الملف `ctimeNs`.
4. أي تغيير بين المرحلتين يُظهر تقرير `BLOCKED` مع السبب العام `TRIAL_CHECKPOINT_CHANGED`، والقيمة `botRights: NOT_CHECKED`، دون كشف تفاصيل الطلاب أو المجموعات أو الملفات.
5. إذا أصبحت حالة STOP الفعلية `RUN` أو اختلّت سلامة النسخة الاحتياطية، تظل أسباب الرفض المحددة الموجودة أصلًا مفضلة.
6. لا تُجرى مكالمات Telegram سوى `getChatMember` للقراءة، ولا يُنفذ حظر أو كتم أو فك تقييد. لا يُنشئ الفحص نسخة احتياطية، ولا يكتب في SQLite أو STOP.

## تغطية TDD

- حالة سليمة: نتيجتان متطابقتان للصلاحيات، وSTOP مستقل ونسخة مستقرة، تعطي `PASS`.
- استبدال ملف STOP بـ STOP مماثل أثناء قراءة الصلاحيات الأولى، وأثناء القراءة الثانية.
- استبدال النسخة الاحتياطية بملف SQLite آخر مطابق منطقيًا أثناء قراءة Telegram.
- إعادة كتابة STOP بالبايتات نفسها داخل inode نفسه، مع اكتشاف تغير وقت الكتابة.
- إعادة كتابة قاعدة البيانات ثم استبدال نسخة احتياطية مطابقة أثناء قراءة الشبكة.
- الانتقال من STOP إلى RUN يُحجب بالسبب المعتاد `SAFETY_NOT_STOP`.

أكدت GitHub Actions فشل حالات الثبات المستهدف قبل الإصلاح، وأُعيد تشغيل المجموعة الكاملة بعد الإصلاح.

## حدود الضمان

هذا فحص محلي استشاري وليس قفلًا حصريًا للملفات، ولا يثبت أن حالة Telegram الخارجية لن تتغير بعد المراقبة، ولا يمنح صلاحية تشغيل عقوبات على مجموعة حقيقية. يجب أن تبقى بيئة الاختبار معزولة، وأي تفعيل حي يتطلب اعتمادًا وتشغيلًا صريحين مع صلاحيات ونسخ احتياطية موثوقة.

**ما يزال إرسال عقوبات Telegram الحية غير مفعّل.**
