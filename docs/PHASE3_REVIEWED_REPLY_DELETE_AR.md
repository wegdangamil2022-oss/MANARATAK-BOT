# المرحلة الثانية والثالثة — تنظيف الرسائل وحذف رسالة بالرد

## المسار المحلي

يربط `/delete` أو `/delete@ManaratakBot`، بالرد داخل مجموعة معتمدة للإشراف، رسالةً ملاحظة مسبقًا بخدمة ModerationPurgeService. يتحقق من معرف المجموعة والرسالة ومؤلفها وتاريخها؛ لا يفهرس نص الرد أو يفترض أن رسالة مجهولة غير محمية. تُرفض رسائل المالك والمشرفين الداخليين، والرسائل غير المفهرسة أو المثبتة أو المحمية وفق metadata المخزنة.

ينشئ الأمر معاينة لرسالة واحدة ويرسل تأكيدًا وإلغاءً إلى الخاص. لا يرسل الحذف عند إنشاء المعاينة. إذا كان الخاص مغلقًا فلا يصل التأكيد ولا تُنفّذ العقوبة. لا تعرض الرسالة الخاصة نص المحتوى أو معرف العضو أو المجموعة.

التأكيد مقيد بصاحب المعاينة ونسخة سياسة المجموعة ومهلة المراجعة وبصمة الرسالة والمرشح. تُقارن البصمة مجددًا **داخل معاملة اعتماد المعاينة**؛ تغيير المراجعة قبل التأكيد أو أثناء انتظاره لا يسمح بحذف هدف مختلف. البصمات أدوات اتساق محلي وليست توقيعًا يحمي من استبدال قاعدة البيانات والزر الأصلي معًا.

عند التأكيد فقط، تحجز خدمة التنظيف المحاولة دائمًا، وتعيد فحص الصلاحيات والحالة قبل الإرسال. لا يُعاد تنفيذ Update مكرر أو تأكيد مستخدم أو نتيجة مجهولة. يعود الإقرار أو التحذير من عدم اليقين في الخاص بتعديل رسالة التأكيد نفسها.

## الزر الرسمي

«🛡️ الحماية والعقوبات ← 🧹 تنظيف الرسائل» أصبح شاشة فعلية لخطط التنظيف المحلية في المجموعات المخولة حاليًا. تدعم الصفحات والتفاصيل والأعداد، وتحجب السجلات ذات المعرفات المتعارضة أو المجموعات المسحوبة. يتوقف اختيار تفصيل قديم عندما تتغير بصمة الخطة.

تتاح أزرار التأكيد والإلغاء للمالك فقط عندما يكون هو صاحب معاينة حديثة لرسالة واحدة والموصل محقونًا في التطبيق. بقية الخطط للعرض، إذ تحتاج المعاينات الجماعية مسار مراجعة منفصلًا. لا تمنح الشاشة صلاحية جديدة ولا تفعّل بوابة الإرسال. أصبح عدد المداخل العليا المرتبطة بشاشات محلية 11 بعد لقطة جرد المرحلة الأولى ذات المداخل العشرة.

## بوابة الحذف

TelegramBotApiPurgeGateway معطلة افتراضيًا وتتطلب بوابة أمان مستقلة ودالة تحقق من الحجز والتفويض الدائمين:

- تقرأ getChatMember للبوت وتتحقق من هويته وحق can_delete_messages؛ وجود رتبة إدارية دون الحق لا يكفي.
- تتحقق من بوابة الإيقاف حول القراءات وعند حد الإرسال. تعيد قراءة حقوق Telegram بعد انتظار التخزين، ثم تعيد التحقق المحلي قبل deleteMessage.
- ترسل معرف الرسالة المعاينة فقط. HTTP ناجح مع true يعطي ACKNOWLEDGED لقبول الطلب؛ لا يمثل إثباتًا ماديًا مستقلًا للحذف.
- تعترف بـ429 صريح ومتوافق فقط وتعيد مهلة مضبوطة. الرد المشوه أو المهلة الشبكية ينتجان UNKNOWN_OUTCOME دون إعادة إرسال عمياء.
- verifyEvidence يعيد false؛ لا يدعي وجود getMessage أو القدرة على استرجاع تاريخ غير متاح.

قوّيت خدمة التنظيف لتربط الإرسال بالمراجعة والمحاولة الأصليتين، وتعزل إقرارًا متأخرًا بعد سحب الاعتماد أو تغيير الدليل إلى UNKNOWN_OUTCOME. بقيت سياسات المعدل والإلغاء والتعارض والاستعادة قائمة.

## التحقق المحلي

```bash
npm run check
node --test dist/tests/telegram-reply-delete.test.js dist/tests/telegram-purge-gateway.test.js
npm run audit:phase1
```

الاختبارات على JSON وSQLite تشمل: المعاينة والتأكيد والإلغاء والانتهاء، المالك والمشرف المفوض، تزوير الضاغط وسياق المجموعة، سحب الاعتماد، حماية الرسالة وعدم تخزين النص، تحريف المرشح قبل التأكيد وأثناء معاملته، النتيجة المجهولة ومنع إعادة المحاولة، الصفحات والاختيارات القديمة، ومرور الضغطة إلى حمولة deleteMessage الدقيقة عبر بوابة API ذات نقل وهمي.

لم تستخدم الاختبارات توكنًا حقيقيًا ولم تتصل بـTelegram. اختُبر فشل ربط المراجعة وفقدان الحقوق أولًا ثم أُصلحا.

## حدود التنفيذ

خادم التشغيل لم يحقن purge أو جامع metadata تلقائيًا؛ الربط الحالي صريح داخل التطبيق والاختبارات المحلية. الرد على رسالة وحده لا يثبت أنها غير مثبتة أو غير محمية، ولذلك يمنع المسار رسالة غير ملاحظة ويحتاج مصدر metadata موثوقًا عند الربط الحي.

الحذف الجماعي عبر الواجهة، وفك الحظر والكتم، والطرد والمدد، وقفل المجموعة والفلاتر ومكافحة السبام ليست مكتملة بهذه الشريحة. لا تمثل هذه النتيجة إغلاق المرحلتين الثانية والثالثة. المرحلة الخامسة مستثناة.

## نتيجة الفحص لهذه الشريحة

نجح typecheck والبناء و2475 اختبارًا دون فشل أو تخطٍّ، والعروض المحلية الستة. نجح الجرد الكامل للأزرار الـ253 على JSON وSQLite؛ بلغ عدد المداخل المرتبطة بواجهات محلية 11، والبقية 242 وصفًا معتمدًا لم تُستكمل وظائفه. لا يثبت ذلك تشغيل Telegram الحي.
